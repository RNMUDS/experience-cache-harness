# PoC実測ログ — qwen3.5:0.8b の構造化出力 (2026-06-03)

> 環境: ollama 0.21.0 (macOS, Metal) / `qwen3.5:0.8b`(1.0GB) / temp=0 / num_ctx=4096 / n=24件(日本語感情分類, pos/neg/neutral 各8)
> スクリプト: `poc_structured_output.py`(本番) , `diag.py`/`diag2.py`(切り分け)

## 結論(数字)

| 条件 | 有効率 | 素直率 | 正答率 | 遅延/件 |
|---|---|---|---|---|
| **A) 0.8B `think:false` + JSONプロンプト(文法なし)** | **100%** | **100%** | **79.2%** | **0.31s** |
| B) 0.8B `think:false` + `format`文法 | 0% | 0% | 0% | 0.14s |
| C) qwen2.5-coder(非thinking) + `format`文法 | 100% | 100% | 100% | 0.83s |

- *有効率* = sentiment が enum 内の妥当JSON / *素直率* = 後処理なしで `json.loads` 成功 / *正答率* = ラベル一致

## 何が起きたか(発見の経緯)

1. **最初、全呼び出しがハング(HTTP 500, 2〜3分)**。原因はモデルでなく**ハーネス設定**:
   - ollama が `qwen3.5:0.8b` を **既定 256K トークン文脈**でロード → KVキャッシュ3.5GiB＋計算グラフ3.1GiB＝合計7.8GiBを確保しスラッシング。
   - **対策: `options.num_ctx` を 4096 に制限** → 123 tok/s で即応答。
2. **`format`(JSON Schema文法)を付けると再びハング**。切り分けの結果:
   - `qwen3.5:0.8b` は **thinking モデル**。`format` は**最終回答のみ**を文法拘束し、**thinkingフェーズは無拘束**。
   - 0.8B は thinking が暴走(1024トークン与えても 3898字 thinking して JSON に未到達, `done=length`, content空) → タイムアウト。
3. **`think:false` にすると速いが、ollama 0.21 は `format` を実質無視**(条件B: 出力が `"positive"` 等の裸テキストで JSON オブジェクトにならず 0%)。
4. **`think:false` + プロンプトで JSON 指示(文法なし)が本命**(条件A): **全24件が後処理不要の妥当JSON**、0.31s。

## 中心的な学び(ハーネス設計へ)

- ✅ **「小型モデルは壊れたJSONを出す」は今回の壁ではなかった。** 真の壁は **thinkingモードの暴走**と**文脈サイズ既定値**という**ハーネス設定**だった。→ 「ハーネスが品質を決める」を実証。
- ✅ **0.8B は短い構造化タスクなら実用。** `think:false`＋JSONプロンプトで **有効率100% / pos・neg は正答100%**(16/16)。
- ⚠️ **正答率の頭打ちは "neutral(中立)" 検出。** 誤り5件は全て neutral(事実文)を pos/neg に誤読(例:「駅から徒歩5分」→positive)。**明確な信号のタスクは得意、微妙な区別は苦手。**
- ❌ **0.8B で `format`文法は当てにしない**(thinkingでハング / think:falseで無視)。**プロンプト指示＋寛容パース＋構造化エラー再試行**でハーネス側が保証する。
- 🛟 **構造保証が要る工程は非thinkingモデルへ。** qwen2.5-coder は `format`文法で **有効100%＋正答100%＋0.83s**。

## 設計指針(本プロジェクトへの反映)

1. **全 ollama 呼び出しに `num_ctx` を明示**(小さく。例:2048〜4096)。既定の巨大文脈は厳禁。
2. **0.8B には常に `think:false`**(高速・決定論)。reasoning が要る時だけ別途、十分な予算で。
3. **出力契約は「プロンプト指示＋寛容パース＋構造化エラーで再試行」**。文法に依存しない。
4. **モデル階層(ルーティング)**: 明確・高頻度の判定 → 0.8B。微妙な判定/構造保証必須 → qwen2.5-coder 等へエスカレーション。
5. **neutral/曖昧クラスは few-shot か明示ルール**でガード(0.8Bの弱点を補助)。
